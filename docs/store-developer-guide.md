# TimeKeeper Store developer guide

This is the technical guide for building, packaging, publishing, installing,
and running a Store extension without changing TimeKeeper Core.

This guide is the implementation-facing companion to
[store-system-architecture.md](store-system-architecture.md), which defines
queues, CRM, logging, security, and lifecycle contracts.

The short version:

> Core owns the stable contract. A Store package implements an existing
> capability in a separate plugin process. Core never imports the package,
> never executes a package-controlled command, and never gives the plugin a
> database handle or Core pointer.

If a plugin needs a capability that does not exist in the stable contract, that
is a Core product/API change for a future reviewed release. It is not something
a plugin may add by mutating Core at runtime.

## Supported integration model

A Store extension has four distinct stages:

```text
source code
   -> reproducible .tkp package
   -> Store catalogue, entitlement and signed download
   -> Core verification and staging
   -> supervised plugin box over timekeeper-bridge/v1
```

An install is not activation. The current Core client verifies and extracts a
package into `.timekeeper/extensions/<product-id>/`; it does not execute the
archive. The supervised bridge launcher and capability adapters are the
execution seam being built next. This deliberate staging-only behavior is a
security property, not a missing shortcut.

## What a plugin developer owns

A plugin project owns:

- the plugin process and its internal implementation;
- its public product id and version;
- a package source directory containing `manifest.json` and payload files;
- the capabilities it declares during the bridge handshake;
- its tests, crash behavior, health endpoint, and logs;
- the Store publication metadata supplied to the Store operator.

A plugin project does not own:

- Core's SQLite database or Go types;
- Core's process, environment, credentials, or arbitrary filesystem paths;
- the Store signing private key;
- entitlement decisions;
- the bridge port, executable selection, timeout, or granted permissions;
- new Core kinds or undocumented capability names.

## Package source layout

A package source directory is ordinary files. The private Store builder creates
`checksums.json`; do not hand-write it.

```text
my-extension-package/
├── manifest.json
├── bin/                         # runtime payload, if the trusted launcher allows it
│   └── my-extension
├── assets/                      # optional data
├── migrations/                  # optional data; never run by Core implicitly
└── checksums.json               # generated by the Store builder
```

The current manifest fields are:

```json
{
  "id": "vendor.memory-galaxy",
  "name": "Memory Galaxy",
  "version": "0.1.0",
  "min_app_version": "0.0.1-alpha",
  "runtime": "timekeeper-bridge/v1",
  "entrypoint": "bin/my-extension",
  "permissions": ["projects.read", "memory.read"]
}
```

`entrypoint` is package metadata, not an instruction that Core may execute.
The trusted launcher selects an executable only from trusted Core policy. A
package must never turn an entrypoint, path, or argument into a request-selected
command.

Permissions are requests, not grants. The Core capability adapter computes the
actual grant from the stable allowlist, user configuration, and product policy.

## Building a package locally

The private `TimeKeeper-Store` repository owns the canonical builder. From that
repository:

```bash
node scripts/genkeys.js       # local development keypair only
npm run seed                  # signed development fixtures
npm test                      # Store contract tests
```

The builder API is `lib/package.js`:

```js
const { build } = require('./lib/package');

const result = build({
  sourceDir: '/absolute/path/to/my-extension-package',
  outputPath: '/absolute/path/to/dist/vendor.memory-galaxy-0.1.0.tkp'
});

console.log(result);
// { path, sha256, size_bytes, signature }
```

The builder:

1. walks regular files below `sourceDir`;
2. writes generated SHA-256 entries to `checksums.json`;
3. creates a deterministic gzip tar archive;
4. hashes the final archive;
5. creates the detached Ed25519 signature over
   `timekeeper-package/v1:<archive sha256>`.

The private signing key stays in the Store operator environment. It never goes
in the plugin repository, package, Core installation, or developer machine
unless that machine is the explicitly isolated local development Store.

`npm run seed` is a fixture generator, not a production publishing workflow.
Production catalogue and package publication remain Store-operator operations;
there is no public client endpoint that lets an extension self-publish.

## Store delivery lifecycle

The public client path is:

```text
GET  /v1/store/extensions
POST /v1/store/claim              (free products only)
POST /v1/store/install
POST /v1/download/request
GET  /v1/download/{ticket}
```

The Store checks identity, authentication, device state, entitlement, product
version, and ticket ownership. The client then:

1. fetches the Store public verification key;
2. downloads the single-use, short-lived ticket stream;
3. hashes the archive;
4. verifies the detached signature;
5. extracts only bounded regular files;
6. verifies `checksums.json` against extracted files;
7. checks manifest identity/version against the Store result;
8. leaves the package staged and inactive.

A checksum proves integrity. The Ed25519 signature proves that the archive was
signed by the configured Store key. Neither proof grants runtime permissions.

## Connecting to Core without Core code changes

The supported Store plugin must be an external process. It speaks the existing
bridge contract rather than importing Core packages.

### 1. Start the plugin box

The trusted launcher starts the executable according to Core policy. The plugin
must not choose its own Core URL, capability port, credentials, or grants.

The control tunnel is the plugin process's stdin/stdout. It is newline-delimited
JSON. Do not write logs to stdout; use stderr or the configured log sink so
control frames cannot be corrupted.

### 2. Complete the handshake

Core sends a hello frame:

```json
{"id":"1","method":"hello","params":{"protocol_version":"timekeeper-bridge/v1","plugin_id":"vendor.memory-galaxy","kind":"knowledge","capability_base":"http://127.0.0.1:43127"}}
```

The plugin replies:

```json
{"id":"1","method":"hello_ok","params":{"protocol_version":"timekeeper-bridge/v1","plugin_id":"vendor.memory-galaxy","declared_capabilities":["knowledge.search"]}}
```

The plugin must refuse or terminate when:

- the protocol version is not exactly `timekeeper-bridge/v1`;
- the requested plugin id is not its own id;
- the hello is malformed;
- a capability is empty or otherwise outside its implementation;
- the capability origin is not the explicit loopback origin supplied by Core.

Capabilities are frozen after `hello_ok`. A plugin cannot widen its authority by
sending a later handshake or response.

### 3. Serve only predetermined capability routes

The capability tunnel is JSON over the explicit loopback HTTP origin. The route
names, request schemas, response schemas, timeout, and permission mapping are
owned by the Core capability adapter. A plugin may implement an existing
capability; it may not invent a route and expect Core to call it.

For example, a `knowledge.search` adapter may define a versioned request and
response such as:

```json
{"query":"checkpoint recovery","limit":20}
```

The exact adapter schema must be documented beside the Core capability contract
before publication. Unknown routes, methods, fields, and capability names must
fail closed.

### 4. Implement health and shutdown

The control tunnel supports these methods:

- `hello` / `hello_ok` — identity and capability negotiation;
- `health` / `health_ok` — bounded liveness/readiness check;
- `shutdown` — graceful stop request;
- `error` — structured refusal with a safe code and optional detail.

The plugin should exit promptly on shutdown, close files and network clients,
and return a non-zero process status for an unhealthy startup or unrecoverable
protocol error. Core treats a dead, hung, or incompatible plugin as
`unavailable`; it does not take down the host application.

## Outbound network rules

The default plugin network policy is `none`. Requesting `network.egress` does
not grant internet access. The Core release/operator must approve a separate
policy containing exact hosts, ports, methods, redirect targets, byte budgets,
request rate, concurrency, and expiry.

Plugins call the Core egress connector; they do not open raw sockets or inherit
Core/Store proxy credentials. The connector resolves DNS, validates TLS, blocks
private/link-local/metadata destinations, prevents IP-literal and DNS-rebinding
bypass, enforces upload/download/response/request/concurrency quotas, and can be
revoked. Body logging is off by default.

A plugin must treat quota exhaustion, connector refusal, and connector loss as
normal bounded errors. It must not retry forever, switch to a different host,
spawn a networking utility, or bypass the connector. A launcher that cannot
install equivalent enforcement must refuse activation.

Example policy shape (Core-owned configuration, not package-controlled input):

```yaml
egress:
  mode: allowlist
  destinations:
    - host: api.example.com
      ports: [443]
      methods: [GET, POST]
  max_requests_per_minute: 60
  max_upload_bytes_per_minute: 1048576
  max_download_bytes_per_minute: 10485760
  max_response_bytes: 2097152
  max_concurrent: 2
```

## Security contract

A plugin must never:

- import `internal/store`, `internal/api`, `internal/model`, or Core private
  packages;
- receive a `*store.Store`, database connection, Core pointer, or Core process
  environment wholesale;
- follow a package-controlled path outside its staged directory;
- execute commands supplied by Store metadata, HTTP requests, or bridge frames;
- bind a non-loopback capability server;
- treat requested permissions as granted permissions;
- send secrets, access tokens, or raw private responses over the bridge;
- write protocol logs to the control stdout stream;
- acknowledge work before the capability operation has actually completed.

Core must not:

- load Store code into its address space;
- execute `manifest.entrypoint` directly;
- allow a package to select its own command, port, timeout, or filesystem root;
- call a capability absent from the frozen handshake allowlist;
- pass raw database rows or unbounded transcript content to a plugin.

## Testing checklist for a plugin release

Before asking the Store operator to publish a version:

- build the plugin from a clean checkout;
- validate the manifest id/version/runtime and requested permissions;
- run the plugin against a fake Core control tunnel;
- test protocol mismatch, wrong id, malformed JSON, duplicate capability,
  unknown capability, timeout, shutdown, and crash behavior;
- prove stdout contains only bridge frames;
- prove the capability server binds only to the assigned loopback origin;
- test oversized requests, path traversal strings, and unknown JSON fields;
- run the Store package checksum/signature verification tests;
- install into a clean Core state directory and confirm it is staged but not
  executed automatically;
- record the package hash, version, tests, and known limitations for the Store
  operator.

## Versioning and compatibility

The bridge protocol is versioned independently from the Store HTTP API. A
plugin declares the bridge protocol in its runtime contract and must fail closed
on mismatch. Backward-incompatible capability schema changes require a new
capability version or a new Core release; silently changing a payload is not
compatible evolution.

The stable-core rule is simple: plugins can add implementations, not host
semantics. The Core team owns the contract, adapters, permission vocabulary,
launcher policy, and lifecycle. Plugin developers own implementations that fit
those contracts.
